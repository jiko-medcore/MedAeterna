# SPEC-06: Canonical Patient-Access Grant Schema

**Status:** Canonical explicit patient-grant table and migration path are selected. A Python reference model and lifecycle tests validate the target contract. No database migration has been created or applied in this specification milestone.

## Decision

Use **`public.patient_access_grants`** as the sole canonical table for explicit, patient-approved practitioner access grants. Do not use `patient_access` as a compatibility table or view.

The existing `patient_access` application query expects `patient_id` and `user_id` only. It has no organization, resource scope, grant status, patient approval, effective period, expiry, or revocation semantics; its `user_id` does not identify a canonical patient-grant recipient contract. The standalone `backend/sql/Patients/create_patient_access_grants_table.sql` is closer because it contains patient, practitioner, organization, access type, status, grant time, and expiry, but it is not a Supabase migration and is not installed in the local database. It is insufficient as-is: key fields are nullable, resource scope and grant/revoke actors are absent, and `assigned` and `emergency` are mixed into the patient-grant type.

This decision covers **explicit patient-approved grants only**. It does not choose a canonical active-treatment/care-team assignment table. SPEC-04 continues to define those as separate relationship evidence, and implementation must not treat either form of relationship as interchangeable.

## Target schema contract

The next approved migration will create or reshape `public.patient_access_grants` with this logical shape:

| Column | Contract |
|---|---|
| `id` | UUID primary key, generated by PostgreSQL. |
| `patient_id` | Required foreign key to `public.patients(id)`. Backend resolves and verifies the patient's authenticated identity; never trust a request value alone. |
| `practitioner_id` | Required foreign key to `public.practitioners(id)`. Recipient must match the verified practitioner identity. |
| `organization_id` | Required foreign key to `public.organizations(id)`; exact organization scope, no null/global grant. |
| `access_type` | Required and constrained to `patient_granted`. `assigned` is a treatment relationship; emergency grants are not supported by the current Phase 0 policy (SPEC-08). Neither belongs in this table. |
| `access_level` | Required and constrained to `read`. These grants never permit clinical writes. |
| `resource_families` | Required, non-empty, unique list drawn only from the SPEC-04 clinical resource catalogue. No unscoped grant. |
| `status` | Required: `pending`, `approved`, `revoked`, or system-set `expired`. `expires_at` is enforced immediately even before a cleanup worker records the `expired` state; no `active` status alias. |
| `requested_by`, `requested_at` | Required request actor and timestamp for traceability. Requesting does not authorize access. |
| `granted_by`, `granted_at` | Required when approved; actor must be the verified patient. A pending row has neither. A verified representative is not supported until a separate policy is approved. |
| `effective_from`, `expires_at` | Required timezone-aware timestamps; expiry must be later than both the grant effective start and approval time. At `now >= expires_at`, the grant no longer authorizes. |
| `revoked_by`, `revoked_at`, `revocation_reason` | Revocation actor/time are required when status is revoked; preserve prior approval fields for approved-then-revoked rows. Revocation is terminal. |
| `created_at`, `updated_at` | Required timezone-aware audit timestamps, maintained by the trusted write path. |

Permit one outstanding row per `(patient_id, practitioner_id, organization_id)` using a partial unique index for `status IN ('pending', 'approved')`; do not put `now()` in an index predicate. A trusted expiry worker (or the new-grant transaction) must mark elapsed pending/approved rows `expired` before inserting a replacement. Expiry is enforced from `expires_at` regardless of worker timing. The row carries the complete resource scope. To change scope, revoke the old row and create a new request/grant; never union rows or mutate an approved row's scope in place. Add indexes for the patient/recipient/organization lookup and the audit foreign key. The companion `public.patient_access_grant_audit` records request, approval, revocation, and system expiry with actor and timestamp; clients cannot update or delete audit entries.

### Lifecycle

| Current state | Next state | Authorized actor |
|---|---|---|
| New request | `pending` | A verified requester; this state grants no access. |
| New direct patient grant | `approved` | Patient-authorized request with patient actor recorded as requester and grantor. |
| `pending` | `approved` | The verified patient only. |
| `pending` | `revoked` | The patient or the original requester may cancel/reject the request. |
| `pending` | `expired` | Trusted expiry worker or transactional grant-creation path, only when `now >= expires_at`. |
| `approved` | `revoked` | The patient only. |
| `approved` | `expired` | Trusted expiry worker or transactional grant-creation path, only when `now >= expires_at`. |
| `revoked` | Any other state | Denied; a new grant requires a new row and approval. |
| `expired` | Any other state | Denied; a new grant requires a new row and approval. |

An `approved` row satisfies only the SPEC-04 patient-grant read relationship when patient, practitioner, organization, resource family, and time all match. It does not grant a role/action, replace a treatment relationship for writes, replace SPEC-05 consent, or enable emergency access.

## Canonical model and tests

The executable schema contract is `backend/app/core/patient_access_grants.py`. It rejects missing or malformed scope, unknown resource families, non-read access levels, legacy `assigned`/`emergency` access types, naive timestamps, invalid approval/revocation/expiry actor fields, and inconsistent grant periods. It includes a reference check for trusted expiry-worker eligibility and maps canonical rows into SPEC-04 normalized grant evidence without asserting that the database source is trusted. Enforcement still belongs in the database and trusted write path.

Focused tests are in `backend/tests/core/test_patient_access_grants_schema.py`. They cover schema constraints, status-event consistency, valid/invalid state transitions, and interoperability with SPEC-04's read-only patient-grant relationship evaluation.

## Migration and cutover path

No data is auto-promoted solely because it exists in a legacy table.

1. **Preflight each environment:** inspect table presence, columns, constraints, indexes, grants, RLS policies, row counts, duplicate active grants, orphaned IDs, status/type values, missing expiry/scope/approval evidence, and every code/job consumer. Production inspection requires an explicitly available project connection and authorization.
2. **Add the target schema:** create `patient_access_grants` and append-only audit storage in an additive Supabase migration. Enable RLS immediately, revoke default client grants, and grant only the required operations. SPEC-11 defines the final table-by-table RLS and grants; Supabase requires grants and policies to be designed together for exposed tables ([RLS guide](https://supabase.com/docs/guides/database/postgres/row-level-security)).
3. **Cut application reads/writes to one source:** replace the `patient_access` query with explicit `patient_access_grants` resolution and SPEC-04 evidence mapping. Do not dual-read or dual-write the old and canonical names.
4. **Reconcile legacy rows conservatively:**
   - `patient_access` rows lack the canonical scope/lifecycle contract and require review or patient regrant; do not translate `user_id` automatically.
   - `patient_access_grants` rows may be carried forward only if recipient, organization, patient, resource scope, patient grant authority, status, and period are independently verified. The current standalone definition has no resource scope or grantor, so its rows cannot be auto-approved.
   - `access_type='assigned'` is evaluated only through the separately authorized treatment-assignment source; it is not converted into a patient grant.
   - `access_type='emergency'` remains denied; SPEC-08 prohibits break-glass access in the current Phase 0 policy.
   - Preserve unresolved rows in a restricted legacy archive or leave them denied pending review. Do not delete audit or historical evidence during cutover.
5. **Verify before retiring legacy access:** run data reconciliation, API allow/deny tests, audit tests, and database RLS/grant tests; confirm no application or background-job reader still uses `patient_access`. Retire or archive that name only in a later migration after consumers and rollback needs are accounted for.

The additive rollout can be rolled back at the application layer without dropping the canonical table or deleting history. Rollback must not restore a legacy path that authorizes rows without explicit scope and lifecycle checks.
